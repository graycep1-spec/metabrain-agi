# MetaBrain MVP — фабрика цифровых сотрудников

Каждый человек в компании получает своих **цифровых сотрудников (ЦС)**: двойника своей роли и новых сотрудников на роли, которых у него нет. ЦС работают постоянно (по расписанию, событиям и вопросам), отвечают с источниками, а действуют в системах только с разрешения **куратора-человека** по лестнице автономии L0 → L1 → L2. Опыт дистиллируется в навыки и через гейт переходит ко всему штату компании.

Принципы: **спеки — source of truth, валидатор-гейт, мета-мозг копит опыт, red-green TDD, контракты до кода.**

## Как устроено

- **Харнесс на человека.** Его ЦС, подключения, память, карта ландшафта, журнал. Данные харнессов изолированы, даже внутри компании.
- **Исследователь** — служебный ЦС харнесса: read-only discovery систем, карта, драфты адаптеров.
- **Каждый ЦС** говорит одним голосом; внутри — скрытый рой: аналитик, разработчик, критик.
- **Валидатор** — отдельный контур: подписывает ответы, паспорта ролей, адаптеры, действия и навыки. Без подписи наружу и в системы ничего не идёт.
- **Мета-мозг** — навыки (личные и компании), policy, eval, retrieval; наружу только MCP.
- **Веб-кабинет** — управление двойником и остальными ЦС: паспорт, автономия, предложения, журнал, подключения, навыки. **Telegram** — вопросы, отчёты и быстрые решения кнопками; через него же вход в кабинет.

LLM — через коннектор к OpenAI-совместимым моделям: внешний DeepSeek в MVP, локальная модель — конфигом.

## Быстрый старт

Установка одной командой — нужен только Docker:

```bash
sudo ./install.sh                                  # Linux-сервер: /opt/metabrain, повторный запуск — обновление
sudo ./install.sh --domain cab.example.ru --email admin@example.ru   # + HTTPS для кабинета (nginx + Let's Encrypt)
```

```powershell
.\install.ps1                                      # Windows 10/11 с Docker Desktop: кабинет на http://localhost:8081
```

Установщик собирает образ, генерирует ключи и пароли, скрыто спрашивает ключ DeepSeek, токен отдельного бота и адрес кабинета, поднимает сервисы и проверяет ключи. Что ставится и как устроено — `deploy/compose.yml`; как провести демо (шаги 1–7) — `DEMO.md`.

Для разработки — `docker-compose.yml` с заглушками и `python -m src.common.demo_env` для `.env`.

Две сборки одного кода: **локальная** (`docker-compose.yml` — разработка и показ на машине) и **веб на VPS** (`deploy/compose.yml` — HTTPS, Telegram OIDC, отдельный бот). Различия и правила — `deploy/README.md`.

Сервис `harness` предоставляет PostgreSQL-backed C-1 API по `POST /v1/operations/{operation}`; Telegram bot при наличии `TELEGRAM_BOT_TOKEN` вызывает его через HTTP-клиент. Сервисы: `web` (кабинет), `validator`, `metabrain` и `metabrain-mcp`, `demo-landscape` (учебные crm/stock/pricing). Проверка готовности: `http://localhost:8080/healthz` (harness) и `http://localhost:8081/healthz` (web).

Локальный secret store использует ссылки вида `env:DEEPSEEK_API_KEY`: Compose передаёт каждую переменную только сервисам, которым она нужна. Валидатор получает свой ключ подписи, харнесс — ключ согласий и ключи LLM, веб-сервис — Telegram bot token. В production секреты должны поступать из внешнего secret store.

**Поставка демо/MVP:** Linux VPS с Docker Engine и Compose за HTTPS reverse proxy. WSL предназначен для локальной разработки; ISO и production-деплой в WSL не предусмотрены. См. ADR-013 в `DECISIONS.md`. Размещение в контуре заказчика остаётся OPEN-06.

## Проверки

```bash
python -m pip install -r requirements-dev.txt
ruff check .
python -m pytest -q
```

Контрактные тесты хранилища T-06/T-07 и HTTP API C-1 (T-35) используют PostgreSQL 16; задайте `TEST_DATABASE_URL`
для локального запуска этих тестов. Без переменной pytest пропускает только PostgreSQL
интеграционные тесты. CI поднимает отдельную тестовую БД, проверяет конфигурацию Compose,
собирает и запускает сервисы с health checks.

## Документы

- **`GUIDE.md`** — руководство для компании: как начать и пользоваться (для кураторов и ИТ).
- **`ARCHITECTURE.md`** — архитектура для технических стейкхолдеров и интеграторов.
- **`deploy/README.md`** — две версии: локальная и веб на VPS; что где запускается и что нельзя смешивать.
- **`docs/ПАМЯТКА.md`** — то же для менеджера на одну страницу; **`docs/БЕЗОПАСНОСТЬ.md`** — для службы безопасности заказчика.
- **`DEMO.md`** — как поднять и провести показ; **`PUBLISH.md`** — публичный репозиторий и релизы.
- **`docs/ideas/`** — концептуальный слой и дорожная карта: видение, инварианты, телеметрия/валидатор, самосовершенствование мета-мозга, автономия (синтез RnD, адаптировано под MetaBrain).

## Как читать репо (для разработки)

1. `AGENTS.md` — правила работы кодинг-агента.
2. `specs/` по порядку: methodology → constitution → glossary → requirements → customer journey → architecture → contracts (C-1…C-6) → roles → tasks → demo-landscape → open-questions.
3. `DECISIONS.md` — почему так (ADR) и кто решил.
4. `INIT-PROMPT.md` — вставить в кодинг-сессию, чтобы начать строить спеку-за-спекой, TDD-first.
