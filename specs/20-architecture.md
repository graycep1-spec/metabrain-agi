# Архитектура — три слоя (харнесс на человека, на VPS)

```
 Люди компании ── веб-кабинет (управление ЦС) ──┐
               └─ Telegram (вопросы, отчёты, кнопки) ┤
                                                 ▼  API харнесса (C-1)
 ┌──────────── СЛОЙ 1 · ХАРНЕСС ЧЕЛОВЕКА (по одному на человека) ─────────────┐
 │  Куратор-гейт: предложения, согласия, решения     Runtime: расписание,     │
 │                                                   события, состояние работ │
 │  Исследователь (служебный ЦС): discovery → карта ландшафта, драфты адаптеров│
 │  ЦС-двойник ┐  паспорт роли + память + уровни автономии (C-6)              │
 │  ЦС новые  ─┘  один голос наружу; внутри рой: аналитик · разработчик · критик│
 │  Адаптеры ландшафта (C-3)            LLM-коннектор → роутер → endpoint (C-2) │
 └──────┬──────────────────────────────────────────────────────────┬─────────┘
        │ ответы, отчёты, действия, паспорта,                     │ skills.resolve,
        │ драфты адаптеров, кандидаты навыков                     │ retrieval, policy
        ▼                                                         ▼
 ┌──────── СЛОЙ 2 · ВАЛИДАТОР (C-4) ───────┐  навык + ScoreCard  ┌──── СЛОЙ 3 · МЕТА-МОЗГ (C-5) ────┐
 │ профили Answer · Passport · Adapter ·    │───────────────────▶│ навыки: личные / компании        │
 │ Action · Skill; подписанный ScoreCard    │                    │ policy · eval · retrieval; MCP    │
 └──────────────────────────────────────────┘                    └───────────────────────────────────┘
```

## Слои

- **Слой 1 — харнесс (на человека).** Куратор-гейт, runtime работ, Исследователь, ЦС владельца, адаптеры, LLM-коннектор. Состояние харнесса — в его изолированном namespace (строки БД с `harness_id`, коллекция вектора на харнесс).
- **Слой 2 — валидатор.** Общий сервис. Всё исходящее и всё применяемое проходит профиль чекеров и получает подписанный ScoreCard. Критик из роя готовит вердикт, подписывает только валидатор.
- **Слой 3 — мета-мозг.** Общий сервис с проекцией: на харнесс (личные навыки, ретривал по данным харнесса) и на компанию (навыки компании, агрегаты). Наружу — только MCP со scope из policy.

## Тенантность

```
Компания (company_id) ─┬─ Харнесс человека A (harness_id) ─ ЦС, подключения, карта, память, журнал
                       ├─ Харнесс человека B
                       └─ Библиотека навыков компании (scope=company)
```

Правило видимости: харнесс читает свои данные + навыки своей компании со `scope=company`. Всё остальное недоступно, проверка — на уровне хранилища и мета-мозга, не только в агенте.

## Потоки

**Работа ЦС.** Триггер (`schedule` / `event` / `ask`) → runtime создаёт job → рой ЦС: аналитик собирает факты (адаптеры `probe`, ретривал, навыки) → критик готовит вердикт → валидатор подписывает → по уровню автономии:
- L0 — отчёт или рекомендация в Telegram;
- L1 — предложение `action` с превью → согласие куратора → `execute` → `verify`;
- L2 — профиль Action → `execute` → `verify` → уведомление куратору.

Всё пишется в журнал.

**Опыт.** Завершённая работа → критик предлагает кандидат навыка → личный навык (через профиль Skill) → по желанию куратора: обезличивание → профиль Skill (scope=company) → согласие автора → библиотека компании → `skills.resolve` в других харнессах.

**Подключение системы.** Куратор просит подключить систему → передаёт доступ (секрет — в secret store) → согласие `connect` → Исследователь драфтит адаптер → профиль Adapter → согласие `adapter` → адаптер активен read-only → discovery → карта.

## Инфраструктура MVP

Один `docker compose` на Linux VPS: `web` (веб-кабинет, ходит только в API C-1), `harness` (API C-1, Telegram-адаптер, runtime, агенты), `validator`, `metabrain`, `postgres`, Qdrant и `nats` (события и шина работ). WSL используется для локальной разработки, не как production runtime; ISO не поставляется (ADR-013). Секреты — в secret store (env/Vault-lite), не в репо.

Bounded contexts (DDD): Channel · Harness · Workforce (ЦС, паспорт, runtime) · Validator · Metabrain · Landscape · LLM. Между ними — только контракты C-1…C-6. Коннекторы ландшафта и LLM — anti-corruption layer.

## Масштабирование

Харнесс — namespace на человека в общем сервисе `harness`; горизонтально — больше воркеров runtime за общим gateway, работы распределяются через NATS. Валидатор и мета-мозг — общие сервисы. Пока — один VPS. Перенос в контур заказчика (OPEN-06) не меняет контракты.
