# Уровень 1 — требования (все верифицируемы)

Колонка **Д**: ✓ — требование входит в демо-срез 48 ч (см. `50-tasks.md`, трек D). Остальные — целевой MVP.

## Харнесс, канал, согласия

| ID | Требование | Проверка | Д |
|---|---|---|---|
| R-01 | Регистрация человека в Telegram создаёт его харнесс (со служебным Исследователем) внутри компании | тест: два человека одной компании не видят ЦС, карту, журнал и память друг друга | ✓ |
| R-02 | Система подключается к харнессу только после согласия куратора; секрет доступа — в secret store | тест: нет `consent_token` → нет подключения; секрета нет в БД, логах, трейсе | ✓ |
| R-03 | Discovery read-only: Исследователь не выполняет мутаций | аудит вызовов адаптера: 100% вызовов Исследователя — `discover`/`probe` | ✓ |
| R-22 | Telegram: вопросы, отчёты, предложения с кнопками «подтвердить / вернуть» | тест: решение по кнопке меняет статус предложения и пишется в журнал; нажатие кнопки чужим Telegram-аккаунтом → отказ | ✓ |
| R-26 | Веб-кабинет управления ЦС: паспорт и его версии, автономия и метрики, пауза, предложения с превью, журнал, подключения и карта, навыки, расписание и события | тест по экранам C-1; правка паспорта и повышение автономии создают предложения, а не меняют состояние | ✓ паспорт, предложения, журнал |
| R-27 | Вход в веб-кабинет — через Telegram Login; кабинет показывает только харнесс вошедшего человека | тест: поддельная подпись, просроченный `auth_date`, незарегистрированный id → `401`; чужой `harness_id` → `403` | ✓ |
| R-28 | Решение по предложению принимается один раз, в любой из двух поверхностей, с одинаковым результатом | тест: решение в кабинете, затем кнопка в Telegram → `409`, в журнале одна запись | ✓ |
| R-23 | Журнал харнесса неизменяем и содержит каждое решение куратора, работу, действие, вызов адаптера и LLM с provenance | тест: попытка изменить/удалить запись → ошибка; E2E-сценарий даёт полный набор записей | ✓ |

## Цифровые сотрудники

| ID | Требование | Проверка | Д |
|---|---|---|---|
| R-14 | Двойник создаётся из текстового описания роли: черновик паспорта → валидатор (профиль Passport) → подтверждение куратора → ЦС активен на L0 | тест: ЦС с неподтверждённым паспортом не запускает работы; новый ЦС стартует на L0 по всем классам | ✓ |
| R-15 | Человек нанимает нового ЦС по паспорту роли в своём харнессе; число ЦС ограничено policy `max_employees` | тест: превышение лимита → отказ с причиной | |
| R-05 | Скрытый рой: человек получает от ЦС один ответ; суб-роли не видны | контракт C-1: в ответах и сообщениях канала нет идентификаторов суб-ролей | ✓ |
| R-04 | Каждый ответ и отчёт ЦС несёт источники; факт без источника блокируется валидатором | golden-набор grounding (C-4) | ✓ |
| R-16 | ЦС работает по расписанию из паспорта без запроса человека; результат приходит в Telegram | тест: срабатывание cron → отчёт в чате; рестарт сервиса посреди работы → работа завершается, шаги не дублируются | ✓ |
| R-17 | ЦС запускает работу по событию из ландшафта (подписка в паспорте) | тест: публикация события в шину → работа нужного ЦС; событие чужого харнесса → не запускает | |
| R-24 | Изменение паспорта — только новой версией через предложение и согласие куратора; ЦС не меняет свой паспорт сам | тест: попытка ЦС записать свой паспорт → блок; новая версия без согласия не активна | |

## Автономия и действия

| ID | Требование | Проверка | Д |
|---|---|---|---|
| R-18 | L1: запись в систему исполняется только после подтверждения куратором конкретного действия; до подтверждения куратор видит превью изменений | тест: `execute` без `consent_token` → блок; предложение `action` содержит `ChangePlan` | |
| R-19 | L2: ЦС исполняет действия разрешённого класса без подтверждения; каждое действие проходит профиль Action и пост-проверку; куратор получает уведомление | тест: действие класса вне policy → блок; провал пост-проверки → инцидент | |
| R-20 | Повышение автономии — только командой куратора и при выполнении порогов policy; иначе отказ с причиной | тест: пороги не выполнены → отказ с перечнем невыполненных метрик | |
| R-25 | Инцидент автоматически понижает пару (ЦС, класс действия) до L0 и уведомляет куратора | тест: инцидент → уровень L0, следующее действие этого класса → блок | |
| R-08 | Драфт адаптера не применяется без ScoreCard валидатора и согласия куратора | тест: применение адаптера без подписи или без согласия → блок | ✓ |
| R-09 | Без подписанного ScoreCard ответ, отчёт, адаптер, действие, паспорт и навык не выходят наружу и не применяются | тест: unsigned или поддельная подпись → блок | ✓ |
