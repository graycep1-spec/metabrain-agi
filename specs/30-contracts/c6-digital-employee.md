# C-6 · Цифровой сотрудник: паспорт роли, runtime, автономия

ЦС = паспорт роли + память + инструменты + уровни автономии + runtime работ. Паспорт — единственный источник того, что ЦС делает, когда и с какими правами.

## Паспорт роли

```
RolePassport {
  employee_id, version, kind: twin | new | researcher,
  harness_id, owner_person_id, curator_person_id,           # в MVP owner = curator
  role {title, mission},
  duties[]  {duty_id, text},
  goals[]   {goal_id, text, metric, target, period},
  decision_bounds {may[], must_not[]},
  escalation[] {condition, to: "curator"},
  tools {connectors[] (connector_id), read_scopes[], write_classes[]},
  triggers {
    schedule[] {cron, duty_id},
    events[]   {subject, filter?, duty_id}
  },
  autonomy {action_class -> L0 | L1 | L2},                    # новый паспорт: все L0
  provenance {source: role_text | template, drafted_by, consent_ref, created_at}
}
```

Как появляется паспорт двойника: человек описывает роль текстом (`employee.draft kind=twin`) → разработчик из роя структурирует текст в паспорт → профиль Passport (C-4) → предложение `passport` → согласие куратора → ЦС `active`. Неясные места в тексте роли попадают в `escalation` и вопросы куратору, а не додумываются.

Статусы ЦС: `draft → active → paused → retired`. Работы запускаются только в `active`.

### Черновик и активация паспорта (T-13)

- **Черновик.** Разработчик роя (LLM, `sub_role=developer`) получает текст роли и возвращает JSON с полями `role`, `duties`, `goals`, `decision_bounds`, `escalation`, `triggers.schedule`. Остальное заполняет харнесс: `employee_id`, `version`, `kind`, `harness_id`, `owner_person_id`, `curator_person_id`, `autonomy = {}`, `provenance`, `tools` — все подключённые системы харнесса и их `read_scopes`, `write_classes = []`. Ответ модели, который не сводится к схеме, — отказ с причиной, паспорт не создаётся. Если в тексте нет расписания, по умолчанию — `*/15 * * * *` на первую обязанность.
- **Проверка.** Паспорт уходит в валидатор (профиль Passport, `curator_scopes` = подключённые системы харнесса). При `fail` предложение не создаётся, куратору — причины.
- **Предложение.** Вид `passport`, предмет `{employee_id, version, passport}`; для новой версии — ещё `previous_version`.
- **Активация.** После согласия харнесс применяет предложение (одноразовый `consent_token`, C-1): версия становится активной, ЦС — `active`. Версии паспорта неизменяемы; прежняя активная версия помечается заменённой.
- **Исследователь** — служебный ЦС без паспорта и триггеров; харнесс заводит его при первом обращении к списку сотрудников.

### Одно ожидающее предложение паспорта

У ЦС не больше одного ожидающего предложения паспорта. Новая версия — правка куратора или расширение `tools` после подключения — строится от последней версии (ждущей решения или действующей) и заменяет прежнее предложение: оно отзывается со статусом `returned`, причиной и без `decided_by`, в журнал — `proposal.withdrawn`. Так три подключения подряд дают одно предложение со всеми системами, а не три версии от одной базы, и подтверждение старой версии не откатывает новую. Если паспорт подтверждён, когда в харнессе уже есть системы, которых в нём нет, сразу предлагается версия с ними.

### Навыки из работы (T-23)

1. Куратор подтверждает предложение `recommendation` → харнесс применяет согласие и просит разработчика роя (LLM, `sub_role=developer`) обобщить рекомендацию в навык: `{title, body, task_class, role_tags[], examples[]}` без имён, номеров и других идентификаторов. Факты работы передаются только плейсхолдерами (DLP).
2. **Личный навык:** кандидат `scope=personal` → C-5 `skill.propose` (профиль Skill) → `skill.publish` без отдельного согласия.
3. **Навык компании:** тот же навык `scope=company`, `source_job_summaries.identifiers` — значения полей с меткой чувствительности и ключи объектов с такими полями из фактов работы → `skill.propose`. При `pass` — предложение `skill_publish` куратору с предметом `{candidate_id, artifact_hash}`; при `fail` — отказ с причинами в журнале, публикации нет.
4. Куратор подтверждает `skill_publish` → харнесс передаёт мета-мозгу `skill.publish` с `consent_token` (C-5) → навык виден всем харнессам компании.

Сбой на шагах 1–3 (бюджет, LLM, мета-мозг) не отменяет решение по рекомендации: в журнал — `skill.failed` с причиной. На шаге 4 мета-мозг недоступен — решение не фиксируется (503), согласие не тратится, куратор повторяет. Журнал харнесса: `skill.published` (scope, `skill_id`, версия), `skill.rejected` (scope, непрошедшие проверки — без самих идентификаторов), `skill.failed`.

### Runtime работ (T-15)

- **Планировщик.** Раз в 30 с проверяет `triggers.schedule` активных ЦС (cron из 5 полей, UTC) за последние 15 минут; на каждый наступивший слот создаёт работу с ключом `(employee_id, duty_id, slot)`. Повторное создание того же слота — без эффекта; пропущенные за время простоя слоты (до 15 минут) догоняются.
- **Одна работа на обязанность:** пока у пары (ЦС, `duty_id`) есть работа в статусе `queued`, `running` или `waiting_curator`, новый слот пропускается.
- **Исполнитель** забирает работу с арендой 5 минут; работа с истёкшей арендой забирается заново. Шаги выполняет **обработчик обязанности** — точка расширения, в которую T-14 подключает рой ЦС. Каждый шаг пишется в БД до и после исполнения; при повторном запуске завершённые шаги не выполняются, их результат берётся из БД.
- **Отчёт** (`report`, C-1) доставляется куратору в Telegram и пишется в журнал харнесса. Пока обработчика нет, планировщик работ не создаёт.

### Рой ЦС (T-14)

Один обработчик для работ по расписанию и для `ask` (C-1 `ask` — работа с триггером `ask`, исполняется сразу в запросе). Шаги:

1. **collect** — факты из систем паспорта (`tools.connectors` с активным адаптером): `discover()` даёт ключи объектов, `probe(ref)` — факты (не больше 40 на работу). Каждый вызов адаптера — в журнал.
2. **analyze** — аналитик (LLM, `sub_role=analyst`) получает роль, задачу (обязанность или вопрос) и факты **только плейсхолдерами** `{{fact:<система>:<ref>.<поле>}}` (DLP — в коннекторе, C-2); возвращает утверждения со ссылками на факты и, если есть, рекомендацию со ссылками.
3. **review** — критик (LLM другого семейства, `sub_role=critic`) отмечает утверждения, которые факты не подтверждают; они удаляются.
4. **validate** — артефакт Answer (C-4): текст собран **только** из оставшихся утверждений, у каждого — источники. Валидатор подписывает ScoreCard, харнесс проверяет подпись (C-4) до выдачи.
5. **propose** — если рекомендация прошла, она становится предложением `recommendation` куратору с теми же источниками (L0: только рекомендация).

**skills** (между collect и analyze): навыки, видимые харнессу (личные и навыки компании, C-5 `skills.resolve`), — последние версии, не больше 5. Аналитик получает их обычным текстом с идентификаторами `skill:<skill_id>@<version>` и может ссылаться на них как на источник: в `sources[]` ответа навык — `{system: "skill", object_ref: "<skill_id>@<version>", skill_ref, read_at}`, где `read_at` — время публикации версии; в тексте ответа — «навык «<название>»» (R-10). Мета-мозг недоступен — работа идёт без навыков.

Если после проверки не осталось подтверждённых утверждений или Answer не прошёл — ответ не выдаётся: человеку — сообщение о блоке, в журнал — `answer.blocked`. Имена суб-ролей не попадают ни в ответ, ни в отчёт (R-05).

## Runtime работ

```
job.start {employee_id, trigger: schedule | event | ask, duty_id?, input?} -> {job_id}
job.state {job_id} -> {status, steps[], waiting_for?}
    status: queued | running | waiting_curator | done | failed
```

- шаг работы фиксируется в БД **до** и **после** исполнения; после рестарта работа продолжается с первого незавершённого шага;
- шаг с записью (`execute`) несёт `idempotency_key` = hash(job_id, step_no) (C-3);
- `waiting_curator`: работа ждёт решения по предложению; по `proposal.decide` продолжается или завершается;
- результат работы: `report` в канал (C-1), предложения, опционально кандидат навыка (`skill.propose`, C-5);
- одновременно у ЦС не больше одной работы на один `duty_id` (повторный триггер → в очередь или пропуск, по policy).

## Автономия

| Уровень | Что разрешено с классом действия | Гейт |
|---|---|---|
| L0 | только `preview`; результат — рекомендация (с `action_class`, если она соответствует записи в систему) | Answer |
| L1 | `execute` после согласия куратора на конкретный `ChangePlan` | Action + consent_token |
| L2 | `execute` без согласия на каждое действие, если класс в `policy.autonomy.allowed_l2_classes` | Action + `post_verify`; уведомление куратору |

- **Новые подключения.** Когда куратор применил адаптер новой системы (C-3), харнесс предлагает каждому активному ЦС (кроме Исследователя) новую версию паспорта с этой системой в `tools`. Без согласия куратора доступ не расширяется.
- **Повышение:** предложение `autonomy_change {employee_id, action_class, from, to, metrics}`. Создать его можно, только если выполнены `promotion_thresholds` (C-5); иначе отказ со списком невыполненных метрик. Применяется после согласия куратора. Прыжок L0 → L2 запрещён.
- **Понижение:** инцидент (провал `post_verify`, кнопка «Инцидент», fail security-чекера на исполненном действии) немедленно ставит пару (ЦС, класс) на L0 и уведомляет куратора. Куратор может понизить уровень сам в любой момент без порогов.
- **Метрики** считаются по журналу: `min_decided` — число решённых куратором предложений ЦС по классу (для L0 → L1 — рекомендации с этим `action_class`, для L1 → L2 — предложения `action`); `accepted_ratio` = принятые / решённые; `eval_score` — по eval-корпусу класса задач; `incident_free_days`. Значения порогов — в policy (C-5).

## Инварианты

- ЦС не пишет свой паспорт и свою автономию (C-010): любые изменения — только через предложения;
- `tools` ⊆ подключённые коннекторы и права куратора (проверяет профиль Passport);
- Исследователь (`kind=researcher`) имеет пустые `write_classes` всегда.

## Планирование: процессы, проекты, назначения и задачи (T-38)

```
Process  { process_id, name, purpose, inputs[], outputs[], status: active | paused | archived }
Project  { project_id, name, goal, starts_on?, ends_on?, budget_usd, status: planned | active | paused | done, result }
Assignment { assignment_id, employee_id, target_type: process | project, target_id, role }
Task     { task_id, assignment_id, employee_id, title, description,
           status: todo | doing | done | blocked, due_at? }
```

- **Изоляция.** Все сущности принадлежат харнессу (`company_id`, `harness_id`). Списки, детали и изменения фильтруются по ним; назначить можно только сотрудника этого харнесса, а процесс/проект — только свой. Повторное назначение того же сотрудника — `409`.
- **Смысл.** Процесс — повторяемое преобразование входов в выходы (разобрать почту, собрать КП). Проект — ограниченный сроком и бюджетом результат. Задача висит на назначении, а не на процессе напрямую: у сотрудника в конкретном процессе/проекте свой набор задач.
- **Кто меняет.** Создание процесса/проекта, назначение и задачи — действие куратора из кабинета, а не автономное действие ЦС. Оно пишется в журнал (`planning.process.created`, `planning.project.created`, `planning.assignment.created`, `planning.task.created`, `planning.task.updated`). Согласие и валидатор для планирования не требуются: это не изменение паспорта и не исходящий артефакт.
- **Примеры.** `planning.seed_examples` идемпотентно создаёт два процесса («Разбор входящей почты», «Подготовка КП по заявке»), проект «Пилот MetaBrain в продажах» и задачи, если у харнесса ещё ничего нет. Сотрудник для примеров — первый не-Исследователь; если его нет, процессы/проект создаются без назначений.
- **Экраны.** `/processes`, `/processes/{id}`, `/projects`, `/projects/{id}`; на `/` — сводка и форма «Создать роль» (`employee.draft`), чтобы было кого прикреплять.
- **Golden.** GT-c6-09 — процесс/проект/назначение/задача; GT-c6-10 — изоляция по харнессу; GT-c6-11 — идемпотентные примеры. Тесты: `tests/test_planning.py`, `tests/test_web_planning.py`.
