# DECISIONS (ADR)

Решения: контекст → решение → последствия. У каждого ADR — источник: автор идеи, команда или кодинг-сессия. Решение команды не выдаётся за слова автора идеи.

## ADR-000 · Шаблон
- **Контекст:** …
- **Решение:** …
- **Последствия:** …
- **Источник:** …

## ADR-001 · Рамка продукта — фабрика цифровых сотрудников
- **Контекст:** T-00 описал продукт как «AI бизнес-партнёр для SMB» с двумя агентами. Автор идеи (Сергей Котов, чат команды 18.10.2026) описывает фабрику цифровых сотрудников: роль → сотрудник с бейджем, ограниченными правами, куратором-человеком и аудитом; опыт дистиллируется в навыки для всего штата. В уточнении того же дня — «цифровые двойники существующих людей + новых», которые постоянно работают в своих ролях на бизнес-цели, переходя от аудита к участию в бизнес-процессах.
- **Решение:** ядро спек — цифровой сотрудник (паспорт роли, куратор, автономия, постоянная работа, навыки). Исследователь и Советник из T-00 не выбрасываются, а встраиваются (ADR-004).
- **Последствия:** переписаны constitution, requirements, architecture, roles, tasks; добавлены глоссарий, C-6, реестр OPEN.
- **Источник:** замысел — автор идеи; выбор рамки для спек — команда, сессия спек 19.10.2026.

## ADR-002 · Харнесс на человека, компания — тенант
- **Контекст:** T-00 заложил «юзерский харнесс». Замысел требует, чтобы опыт работал на весь штат.
- **Решение:** харнесс — на человека (сотрудника компании). Компания — тенант, объединяющий харнессы и библиотеку навыков компании. Между харнессами данные изолированы; общий только опубликованный навык (ADR-003).
- **Последствия:** у каждой записи данных есть `company_id` и `harness_id`; ретривал и журнал фильтруются по `harness_id`, навыки — по `company_id` + `scope`.
- **Источник:** команда, сессия спек 19.10.2026.

## ADR-003 · Обмен опытом — только навыками через гейт
- **Контекст:** изоляция харнессов (ADR-002) против «навыки бустят весь штат».
- **Решение:** кандидат навыка обезличивается, проходит профиль валидатора Skill, затем автор-куратор соглашается на публикацию. После этого навык виден всем харнессам компании (C-012).
- **Последствия:** в C-4 появился профиль Skill, в C-5 — `skill.propose` и `scope: personal | company`.
- **Источник:** команда, сессия спек 19.10.2026.

## ADR-004 · Исследователь — служебный ЦС; паттерн Советника — у каждого ЦС
- **Контекст:** в T-00 видимых агентов два: Исследователь и Советник со скрытым роем. В рамке ADR-001 человек общается со своими ЦС.
- **Решение:** Исследователь — служебный ЦС, который есть в каждом харнессе (read-only discovery, карта, драфты адаптеров). Паттерн Советника («один голос наружу, внутри аналитик · разработчик · критик») применяется к каждому ЦС — двойнику и новым. Отдельного ЦС «Советник» нет.
- **Последствия:** C-1 адресует вопросы конкретному ЦС (`employee_id`); роли в `40-roles.md` описаны как шаблон ЦС.
- **Источник:** предложение сессии спек 19.10.2026; подтверждено командой 20.10.2026.

## ADR-005 · Постоянная работа — расписание + события
- **Контекст:** автор идеи требует постоянной работы в роли; механизм не задан.
- **Решение:** триггеры работы — `schedule` (cron из паспорта), `event` (сообщения шины NATS от адаптеров), `ask` (вопрос человека). Состояние работы — в Postgres, шаги идемпотентны. В демо-срезе — только `schedule` и `ask`.
- **Последствия:** контракт C-6 (job API), требования R-16, R-17.
- **Источник:** команда, сессия спек 19.10.2026.

## ADR-006 · Автономия L0–L2 в целевом MVP, демо — L0
- **Контекст:** черновая лестница автономии из питча (L0 рекомендации, L1 после согласования, L2 в пределах политик).
- **Решение:** целевой MVP реализует все три уровня на пару (ЦС, класс действия). Демо 48 ч — только L0.
- **Последствия:** C-3 получил `preview/execute/verify`, C-4 — профиль Action, C-6 — правила повышения/понижения; пороги — OPEN-04.
- **Источник:** лестница — черновик питча; объём MVP — команда, сессия спек 19.10.2026.

## ADR-008 · Подпись ScoreCard и согласий
- **Контекст:** проверка согласия не должна требовать приватный ключ; ключ подписи одного харнесса не должен совпадать с ключом другого.
- **Решение:** ScoreCard подписывается Ed25519 по каноническому JSON (RFC 8785, JCS). Приватный ключ есть только у валидатора, остальные проверяют по публичному. Корневой `CONSENT_SIGNING_KEY` доступен только харнессу; из него HKDF-SHA256 с `harness_id` выводит отдельный ключ подписи согласий для каждого харнесса. Корневой ключ удостоверяет публичный ключ харнесса в `key_certificate`; подпись токена проверяется по этому ключу. C-1 и C-5 доверяют только корневому `CONSENT_PUBLIC_KEY`, не приватному ключу.
- **Последствия:** формат зафиксирован в C-4, C-1 и C-5; golden проверяют сертификат, подделку и повтор. Срок токена задаёт `CONSENT_TOKEN_TTL_SECONDS` (по умолчанию 900, допустимо 1–86400).
- **Источник:** сессия спек 19.10.2026.

## ADR-009 · Процесс демо — обработка заявок и заказов
- **Контекст:** OPEN-01: процесс не выбран, демо-ландшафт был абстрактной заглушкой.
- **Решение:** демо и E2E строятся на обработке заявок: двойники двух менеджеров разбирают заявки по учебным системам `crm`, `stock`, `pricing` и готовят КП; навык «предложить аналог при нехватке» переходит от A к B (`specs/60-demo-landscape.md`).
- **Последствия:** заданы фикстура, классы действий и golden GT-dl-01..05. Контракты не меняются; при смене процесса меняется только `60-demo-landscape.md`.
- **Источник:** команда, 20.10.2026. Автор идеи этот выбор **не подтверждал** (на слайдах питча был ИТ-ландшафт); вопрос ему отправлен.

## ADR-010 · Вход в компанию — инвайт-ссылка
- **Решение:** первый человек при `/start` без инвайта создаёт компанию и получает инвайт-ссылку; остальные регистрируются по ней. Ссылку может выпустить любой участник, она многоразовая до истечения срока.
- **Последствия:** в C-1 `company.invite`, `/invite`, GT-c1-08.
- **Источник:** команда, 20.10.2026.

## ADR-011 · Стартовые пороги автономии
- **Решение:** L0 → L1: ≥ 10 решённых рекомендаций класса, принято ≥ 80%. L1 → L2: ≥ 20 решённых действий, принято ≥ 90%, eval ≥ 0,9, 14 дней без инцидентов. Это параметры policy, а не константы кода.
- **Последствия:** значения в C-5 `promotion_thresholds`, правила подсчёта в C-6.
- **Источник:** команда, 20.10.2026; калибровка — по данным пилота.

## ADR-012 · Веб-кабинет управления цифровым двойником с первой версии
- **Контекст:** ADR-007 оставлял в MVP только Telegram. Автор идеи сказал закладывать веб-интерфейс сразу и делать в нём управление цифровым двойником.
- **Решение:** две поверхности поверх одного API C-1. Веб-кабинет — управление ЦС: паспорт и версии, автономия и метрики, пауза, предложения с превью, журнал, подключения и карта, навыки, расписание и события. Telegram — вопросы, отчёты, быстрые решения кнопками. Вход в кабинет — Telegram Login. В демо 48 ч — экраны «Сотрудники», «Паспорт», «Предложения», «Журнал».
- **Последствия:** C-1 расширен (вход, экраны, операции управления ЦС, `409` на повторное решение); требования R-26..R-28; сервис `web` в compose; задачи T-31..T-34. Стек фронтенда выбирает кодинг-сессия (ADR).
- **Источник:** «веб сразу, в нём управление двойником» — автор идеи, передано Анной 20.10.2026. Состав экранов, роль Telegram, вход и объём в демо — команда, 20.10.2026.

## ADR-013 · Стек приложения и поставка MVP
- **Контекст:** T-01 требует воспроизводимый каркас и smoke-проверку развёртывания. MVP должен поддерживать Telegram и веб-кабинет, оставаясь простым для эксплуатации одной командой.
- **Решение:** backend и сервисы — Python 3.12, FastAPI для HTTP API, aiogram для Telegram, pytest и Ruff для проверок. Веб-кабинет — серверные шаблоны Jinja2 + HTMX: отдельный frontend runtime не нужен, кабинет и API используют same-origin сессию. Операционные данные — PostgreSQL 16, векторный индекс — Qdrant, шина работ — NATS 2. Для демо и MVP поставка — `docker compose` на Linux VPS за HTTPS reverse proxy; WSL — только среда разработки, ISO не собираем. Размещение в контуре заказчика остаётся отдельным будущим вариантом (OPEN-06).
- **Последствия:** инфраструктурные сервисы и `web` включены в compose; один и тот же Compose-сценарий используется для разработки, CI smoke-теста и Linux VPS. Выбор Qdrant закрывает OPEN-09; фильтрация данных по `harness_id` остаётся обязательной на стороне сервиса, а не клиента. Текущий T-01 scaffold — заглушки готовности, а не реализация продуктовых API.
- **Источник:** кодинг-сессия, 20.10.2026; выбор стека в рамках T-01.

## ADR-014 · Env secret store для локального MVP
- **Контекст:** T-02 требует загрузку конфигурации и секретов для ключей LLM, Telegram, валидатора и куратора. Формат ссылок должен одинаково работать в локальном Compose и допускать переход на production secret store.
- **Решение:** локальный store разрешает только ссылки `env:UPPERCASE_NAME` в переменные окружения процесса. Конфигурация хранит ссылки, а не значения секретов; отсутствующий или пустой секрет вызывает явную ошибку. Compose передаёт секреты allow-list по сервисам: LLM и ключ куратора — `harness`, ключ валидатора — `validator`, Telegram bot token — `harness` и `web`, пароль БД — только `postgres`. Внешний secret store для production не меняет формат ссылок; значения не попадают в репозиторий или Docker build context.
- **Последствия:** добавлены типизированный загрузчик настроек и `EnvSecretStore`; `.env` остаётся локальным источником для Compose и исключён из Git и build context. Загрузка/ротация внешних секретов и криптографический формат ключей остаются в границах последующих задач C-1/C-2/C-4.
- **Источник:** кодинг-сессия, 20.10.2026; решение реализации T-02 по C-003 и ADR-008.

## ADR-015 · Открытый вопрос потока `/connect` в Telegram
- **Статус:** закрыт 20.10.2026: handoff через `landscape.connect.start` → `cabinet_url` → форма доступа в кабинете → `landscape.connect` с `secret_ref` (C-1, «Подключение, начатое в Telegram», GT-c1-15).
- **Контекст:** C-1 описывает `landscape.connect` с `secret_ref`, но запрещает вводить секрет в Telegram; секрет должен поступить через веб-кабинет.
- **Временное решение:** Telegram-адаптер передаёт только идентификатор системы и Telegram identity; он не принимает и не пересылает секрет. Пользователю предлагается добавить доступ в веб-кабинете.
- **Последствия:** до реализации API-моста надо определить, как запрос из Telegram связывается с `secret_ref`, созданным в веб-кабинете. Подключение не должно применяться, пока валидный `secret_ref` не доступен.
- **Источник:** реализация T-09 по C-1; точный handoff между поверхностями в спеках не определён.

## ADR-016 · Набор профилей валидатора `demo-v1`
- **Контекст:** профиль Answer требует судью (LLM другого семейства), профиль Skill — eval на корпусе задач. В демо-срезе нет ни судьи, ни eval-корпуса. Гейт закрыт по умолчанию, поэтому с полным составом ни один ответ и навык в демо не прошли бы.
- **Решение:** два набора профилей. `mvp-v1` — полный состав C-4. `demo-v1` — без `judge` в Answer и без `eval` в Skill, всё остальное как в `mvp-v1`. Набор записывается в подписанный ScoreCard (`profile_set`), выбирается конфигом сервиса; по умолчанию в compose — `demo-v1`, по умолчанию в коде — `mvp-v1`.
- **Последствия:** в демо ответ проверяется только детерминированно (источники, PII). Переход на `mvp-v1` требует реализовать `judge` и `eval` навыка (T-12 полный объём).
- **Источник:** поток S (спеки), 20.10.2026.

## ADR-017 · Sandbox адаптера в демо-срезе
- **Контекст:** C-4 требует запуск драфта адаптера на тест-данных без доступа к боевым и предполагает чекеры-контейнеры. Отдельный контейнер на каждый прогон в демо-срезе — лишняя инфраструктура.
- **Решение:** адаптер не получает ни секретов, ни сети по контракту (C-3, «Среда исполнения»). Проверка двухслойная: статический разбор (security: список разрешённых импортов, запрет опасных вызовов и dunder-доступа) и запуск в отдельном процессе Python с `-I -S -B`, пустым окружением, таймаутом и audit-hook, который блокирует сеть, процессы, нативный код и файлы вне каталога драфта. Данные — тест-стенд из фикстуры `demo-landscape`.
- **Последствия:** audit-hook Python — не граница безопасности; защиту держит связка «статический разбор + hook + отсутствие секретов в окружении». Для целевого MVP — отдельный контейнер без сети на прогон (OPEN-12).
- **Источник:** поток S (спеки), 20.10.2026.

## ADR-018 · Мета-мозг в демо-срезе: Postgres, полнотекстовый ретривал, политика-файл
- **Контекст:** ADR-013 выбрал Qdrant для векторов, но векторам нужны эмбеддинги, а у DeepSeek эндпоинта эмбеддингов нет. Политик компаний и интерфейса их правки в демо-срезе тоже нет.
- **Решение:** Skill Library, кандидаты, использованные согласия, Retrieval Index и журнал мета-мозга — в Postgres. Ретривал — полнотекстовый (`russian` + `simple`, OR по словам запроса) с фильтром по `company_id`/`harness_id` в SQL. Политика — версионируемый JSON-файл в репо (`src/metabrain/policy/default.json`), одна на установку. Маршруты моделей обновлены по ADR-021: роли аналитика, разработчика и исследователя используют `deepseek-flash`, критик — `deepseek-v4-pro`; историческая ссылка на `deepseek-chat`/`deepseek-reasoner` больше не актуальна. Мета-мозг проверяет ScoreCard по ключам валидатора (`GET /v1/keys`), а `consent_token` — по публичному ключу куратор-гейта из конфига (`CONSENT_PUBLIC_KEY`).
- **Последствия:** Qdrant в compose пока не используется продуктом; векторный ретривал — после выбора провайдера эмбеддингов (OPEN-14). Лимиты в политике `null` до решения по OPEN-13.
- **Источник:** поток S, 20.10.2026.

## ADR-019 · Своя роль БД у каждого сервиса
- **Контекст:** ADR-014 оставляет пароль суперпользователя Postgres только сервису `postgres`. Мета-мозгу (а в T-35 — харнессу) нужна своя БД-учётка.
- **Решение:** при инициализации пустого тома `deploy/postgres/init/10-service-roles.sh` создаёт для сервиса роль и одноимённую схему, роль владеет только своей схемой и по умолчанию работает в ней. Пароль роли — отдельный секрет (`METABRAIN_DB_PASSWORD`), сервис получает только URL со своей ролью. Новый сервис = ещё один вызов `create_service_role` и свой `*_DB_PASSWORD`.
- **Последствия:** таблицы мета-мозга недоступны харнессу и наоборот. Init-скрипт срабатывает только на пустом томе: после добавления роли локально нужен `docker compose down -v`. Роли с правами только на DML (без владения таблицами) — вместе с ревью журнала (фикс-пакет, п. 7).
- **Источник:** поток S, 20.10.2026.

## ADR-020 · Граница T-35 и runtime `ask`
- **Статус:** принято в кодинг-сессии; проверка Stream S остаётся частью ревью коммита.
- **Контекст:** T-35 предшествует T-14, T-19 и T-31, но исходная строка задач включала GT-c1-01 — `ask` по подключённой демо-системе с источниками и ScoreCard. T-14 реализует цифрового сотрудника и `ask`, T-19 — исследование и адаптеры, T-31 — кабинет для ввода доступа. C-1 описывает предложение `connect`, но не применение подключения к runtime.
- **Решение:** сохранить GT-c1-01 без ослабления, но отнести его приёмку к T-14. T-35 отвечает за HTTP API, регистрацию, приглашения, операции демо-среза и Telegram-клиент; `ask` route проверяет идентичность и изоляцию, а до реализации runtime явно отвечает `501 not_implemented`. Не выдавать тестовый или незаземлённый ответ за продуктовый.
- **Последствия:** T-35 можно принять после прохождения её собственных golden и CI; GT-c1-01 остаётся обязательным гейтом T-14. Применение согласованного подключения остаётся границей T-19/T-31 и должно быть реализовано до сквозного сценария GT-c1-01.
- **Источник:** кодинг-сессия, 20.10.2026; решение по несоответствию границ задач в `specs/50-tasks.md` и контракте C-1.

## ADR-021 · Бюджет демо — 5 $ DeepSeek; модели V4
- **Контекст:** Анна задала лимит активности «условные 5 $ DeepSeek» (20.10.2026). При проверке цен выяснилось, что DeepSeek вывел из обращения имена `deepseek-chat` и `deepseek-reasoner` (24.07.2026); актуальны `deepseek-flash` (V4.1-Flash) и `deepseek-v4-pro`. Цены на 20.10.2026, за 1M токенов, пиковый тариф: flash — вход 0,30 $ (кэш 0,006 $), выход 1,20 $; v4-pro — вход 1,32 $ (кэш 0,044 $), выход 3,96 $. Вне пика — вдвое дешевле.

Стоимость считается по пиковой цене без скидки за кэш, поэтому учтённая сумма не меньше счёта. Маршруты: аналитик, разработчик, Исследователь — `deepseek-flash`, критик — `deepseek-v4-pro`.
- **Последствия:** политика-ориентированные `PolicyBudgetGuard` и `PolicyCostCalculator` хранятся в `src/llm/budget.py`; PostgreSQL харнесса фиксирует фактическое использование и атомарные preflight-резервации. Реальные вызовы разрешать только после подключения этих компонентов при сборке runtime T-14. Демо на двух людей за 48 ч укладывается: 2 харнесса × 2 суток × 1 $ = 4 $ ≤ 5 $. Значения по умолчанию в конфиге и compose: `deepseek-flash` для основных ролей и `deepseek-v4-pro` для критика; base URL — `https://api.deepseek.com`. Роутинг ролей уже описан в политике C-5; его подключение к runtime остаётся в границах T-14.
- **Источник:** лимит — Анна, 20.10.2026; цены — https://api-docs.deepseek.com/quick_start/pricing/; разбиение лимита и маршруты — поток S.

## ADR-027 · Навыки в демо-срезе: из одобренной рекомендации, без подбора по релевантности
- **Контекст:** T-23 требует, чтобы опыт ЦС становился навыком и через гейт переходил к другим (C-012, R-10, R-21). Классификатора задач нет.
- **Решение:** навык рождается только из рекомендации, которую подтвердил куратор: разработчик роя обобщает её, личная версия публикуется сразу, версия для компании — через профиль Skill и предложение `skill_publish`. ## ADR-028 · Хранилище секретов харнесса (vault-lite) для доступов из кабинета
- **Контекст:** C-1 требует, чтобы доступ к системе вводился в форме кабинета и попадал в secret store, а наружу шла только ссылка (GT-c1-13). Env secret store (ADR-014) только читает переменные окружения: секрет, введённый человеком, в нём не сохранить. Демо подключает `demo-landscape` именно этим путём.
- **Решение:** таблица `harness_secrets` в БД харнесса: секрет шифруется AES-256-GCM ключом `SECRET_STORE_KEY` (32 байта, base64, из env secret store); в AAD — версия схемы, `harness_id`, `secret_id` и система, поэтому шифротекст не переносится в другой харнесс или систему. - **Последствия:** без `SECRET_STORE_KEY` ввод доступа в кабинете отвечает 503, подключение по `env:`-ссылкам работает как раньше. Смена ключа — перешифровка таблицы (позже). Внешний Vault для production меняет только реализацию `vault:`, формат ссылок остаётся.

## ADR-029 · Модуль самосовершенствования — только через гейт (операционализация C-006)
- **Контекст:** нужен модуль, где агент-отладчик видит телеметрию работающего экземпляра и дорабатывает его. Риск: автономная самоправка в проде без человека ломает C-005 (детерминированный гейт), C-006 (непроверенное не применяется) и C-010 (ЦС не меняет свой паспорт/права/автономию) — и обрушивает всю модель доверия, описанную в `docs/БЕЗОПАСНОСТЬ.md`.
- **Решение:** самосовершенствование — **операционная петля над C-006**, не автономная самоправка.
  1. Сабролью `debugger` рой читает **свою** телеметрию харнесса (журнал: `answer.blocked`, упавшие работы, ошибки `adapter.call`, повторяющиеся `ask` без ответа, отказы валидатора, расход). Только обезличенные записи — секретов и ПДн там уже нет (DLP, C-2).
  2. Отладчик ставит диагноз и **драфтит улучшение как артефакт**: починка/новая версия адаптера (C-3), кандидат навыка (C-5), предложение изменения паспорта или расписания (C-6).
  3. Артефакт → валидатор (профиль Adapter/Skill/Passport) → **предложение куратору** → согласие → применение к запущенному экземпляру через уже существующие версии артефактов.
- **Границы (что модуль НЕ делает):** не применяет изменения автономно; не переписывает код сервиса (это обычный релиз, не этот модуль); не меняет собственный паспорт/права/автономию ЦС (C-010); телеметрия наружу не уходит, а если выгружается для анализа — обезличенная и в контролируемое хранилище, не сырьём в git. Автономные действия возможны только в пределах уже включённой человеком лестницы автономии L1/L2 по классам действий, с пост-проверкой (C-011).
- **Последствия:** улучшаются только артефакты, уже находящиеся под гейтом; «буст по телеметрии» — это поток предложений куратору, а не самоизменение. Реализация — T-37.
- **Источник:** команда, 23.10.2026.

## ADR-030 · Саморегистрация: создание организации в кабинете
- **Контекст:** вход в кабинет требовал, чтобы человек уже был зарегистрирован в боте (`/start`); иначе — тупик «зарегистрируйтесь в боте». Для продукта нужен бутстрап организации прямо в кабинете.
- **Решение:** если Telegram-личность подтверждена OIDC-колбэком, но организации ещё нет, харнесс выдаёт **одноразовый тикет саморегистрации** (`web_bootstrap_tickets`, хэш, срок 15 мин). Кабинет показывает экран «Создание организации»; по тикету операция `auth.web.bootstrap {ticket, company_name}` регистрирует эту личность с выбранным названием (человек становится куратором своего харнесса) и открывает сессию. Тикет в cookie `mb_bootstrap` (HttpOnly, Secure, SameSite=Lax — cross-site POST его не унесёт, это и есть защита от CSRF до появления сессии).

Код приглашения (`company_invites`, тот же хэш и 7-дневный срок, что у `company.invite` в боте) резолвится в `company_id` **до** гашения тикета — опечатка не сжигает вход. По коду личность регистрируется в уже существующей орг (`register_person(trusted_company_id=…)`), в своём отдельном харнессе; шаблон организации (пример-сотрудник, процессы) при присоединении **не** пересеивается — он только у создателя орг. Куратор генерирует код в кабинете кнопкой «Пригласить коллегу» (операция `company.invite`), код принимается как голый, так и внутри ссылки `t.me/<bot>?start=…`.

## ADR-031 · Telegram OIDC: nonce опционален, ошибки token endpoint — в лог
- **Контекст:** 23.10.2026 вход на боевом стенде доходил до Telegram, но `/auth/callback` возвращал 401; причина в UI не видна. Разбор: state находится, сессия не создаётся; повторный обмен кода Telegram отдаёт `invalid_grant`, клиентский секрет при этом принимается. В ручном OIDC-flow Telegram не гарантирует `nonce` в `id_token`, а код требовал его безусловно; fake-провайдер в тестах nonce присылал, поэтому тесты были зелёными.
- **Решение:** `nonce` проверяется, если он есть в `id_token`; если его нет — вход принимается, защита остаётся на одноразовом `state` и PKCE. Если token endpoint вернул 200 с объектом `error` (например, `invalid_grant`), это `token_exchange_failed`, а не `id_token_missing`. `id` из `id_token` принимается числом или строкой из цифр. Ошибки token endpoint и отклонения `id_token` пишутся в лог harness без токенов и секретов.
- **Последствия:** реальный Telegram OIDC проходит без nonce; подделка/повтор state и PKCE по-прежнему блокируются. Если Telegram начнёт возвращать nonce, он будет сверяться. В логах появится точная причина следующего сбоя (класс PyJWT или error token endpoint).
- **Источник:** инцидент 23.10.2026, проверка на боевом стенде.

## ADR-032 · Планирование живёт в харнессе; кросс-харнесс — отдельно
- **Контекст:** куратору нужны процессы (повторяемое преобразование входов в выходы), проекты (ограниченный сроком/бюджетом результат), прикрепление сотрудников и задачи. В продукте харнесс — граница изоляции данных человека; C-010 требует, чтобы ЦС не расширял себе права.

Создание и назначение — действие куратора из кабинета, пишется в журнал; валидатор/consent не нужны, потому что это планирование, а не паспорт и не исходящий артефакт. - **Источник:** запрос пользователя, 23.10.2026; T-38.


## ADR-033 · Настройка LLM в кабинете
- **Контекст:** для коробки в контуре заказчика нужно переключать LLM (внешний DeepSeek ↔ локальная модель) без правки `.env` по SSH: админ должен задать провайдера, адрес, имена моделей и ключ через веб-кабинет. При этом нельзя трогать политику (маршруты ролей, цены, лимиты, семейства) и нельзя позволить арендатору на общем облаке менять LLM всей установки.
- **Решение:** таблица `llm_settings` (одна строка на установку) хранит provider/api_base/model_main/model_judge/dlp/`api_key_ref`; ключ шифруется в vault (`harness_secrets`, система `llm`), наружу и в журнал — только ссылка. На старте харнесса `overlay_settings` накладывает строку на env-конфиг; `build_connector` берёт адрес и ключ из конфига, имена моделей — из настроек (судья = `critic`, остальные = основная), а семейства/цены/маршруты — по-прежнему из политики. Коннектор собирается один раз на процесс, поэтому **изменения применяются после перезапуска харнесса** (кабинет это проговаривает). Операции `settings.llm.get` (чтение), `settings.llm.put` и `settings.llm.test` (проверка `GET /models`); запись и проверка требуют CSRF и включаются флагом установки `LLM_SETTINGS_EDITABLE` (по умолчанию выкл. — экран показывает конфиг только для чтения). Внешний провайдер без DLP запрещён (инвариант коннектора продублирован в валидации).
- **Последствия:** на общем облачном стенде экран «Настройки» только показывает конфиг; редактирование включают на одно-арендной коробке. Ключ из кабинета резолвится любым процессом с БД и `SECRET_STORE_KEY` (AAD в vault — целостность, не разграничение доступа). `LLM_MODEL_MAIN/JUDGE` из env перестали быть «мёртвыми» — теперь уходят провайдеру как имя модели.
- **Источник:** запрос Анны «deepseek с интерфейсом настройки LLM внутри», 23.10.2026.

## ADR-034 · Каталог ролей/процессов, видимый конвейер и диагност
- **Контекст:** куратору нужно получать работающих ЦС за минуты, а не описывать каждую роль с нуля; при сбоях сотрудника нужен разбор без разработчика. Запрос Анны: «преднастроенные роли, процессы, конвейер — минимум по спекам» и «диагност, который правит багу через помощь».
- **Решение:** каталог (`src/workforce/catalog.py`): готовые черновики паспортов (provenance.source="template", без LLM) и заготовки процессов; оба идут штатным конвейером — валидатор → предложение → гейт куратора (новая орг сеется из того же каталога). Конвейер найма показан в кабинете стадиями с числом ожидающих гейта. Диагност (`employee.diagnose`): рой сотрудника получает дайджест его журнала + вопрос куратора тем же путём, что `ask`; диагноз возвращается куратору, рекомендация — обычным предложением, после согласия становится навыком (ADR-027). Никакой автономной правки кода/паспортов — только через гейт (ADR-029, C-006).
- **Последствия:** каждая роль каталога закреплена тестом «проходит валидатор»; изменение схемы паспорта ломает тест, а не кабинет. Диагност тратит бюджет LLM как обычный `ask` и подчинён тем же лимитам (ADR-021) и DLP.
- **Источник:** Анна, 23.10.2026.

## ADR-035 · Профиль организации и авто-вызов диагноста
- **Контекст:** роли создавались без знания о компании (отрасль, размер, KPI), каталог процессов был безотраслевым, а диагност вызывался только кнопкой — упавшая по расписанию работа оставалась незамеченной до захода куратора.
- **Решение:** таблица `org_settings` (одна строка на компанию): отрасль (справочник), размер, KPI ≤500 зн.; операции `org.get`/`org.put`, экран «Организация». Наследование вниз: роль из каталога получает KPI отдельной целью (`metric=org_kpi`, детерминированно), роль из свободного описания — контекстом организации в промпте модели. Каталог процессов размечен отраслями (SME: продажи, услуги, производство, логистика, розница, ИТ — по ≥2 на отрасль + универсальные); процессы отрасли организации показываются первыми. Авто-диагност: упавшая работа runtime сама ставит диагностическую работу тем же роем (ADR-034) — не чаще раза в 6 часов на сотрудника, упавшая диагностика себя не диагностирует, отчёт уходит куратору, рекомендация — предложением через гейт.
- **Последствия:** профиль правит любой куратор компании, изменение журналируется (`org.updated`); авто-диагност тратит бюджет как обычный `ask` и подчинён лимитам (ADR-021); сбой авто-помощи не роняет runtime.
- **Источник:** Анна, 23.10.2026.
