# MetaBrain для службы безопасности заказчика

Документ для ИБ-службы, оценивающей MetaBrain: изоляция, защита данных, контроль доступа, аудит и размещение в контуре. Технические подробности — `ARCHITECTURE.md` и `specs/` (контракты C-1…C-6, конституция). Отметки: **[есть]** — реализовано и проверено; **[MVP]**/**[план]** — в разработке.

## Модель угроз и ответ

| Риск | Как закрыт |
|---|---|
| Агент получает доступ, которого ему не давали | Агент не выдаёт себе доступ. Любое подключение и права — только по явному согласию человека-куратора. Права ЦС не шире прав куратора в системе. **[есть]** |
| Утечка данных во внешнюю модель | Перед отправкой — DLP: факты идут плейсхолдерами, значения фильтруются по меткам чувствительности; персональные данные клиента не покидают контур. DLP нельзя отключить для внешнего провайдера. **[есть]** |
| Доступ одного пользователя виден другому | Изоляция на уровне хранилища, не только в агенте: каждый читает свои данные и навыки своей компании; чужое и другие компании недоступны. **[есть]** |
| Подмена или повтор решения | Согласие — одноразовый токен, подписанный Ed25519 по канонизации JCS, привязан к предмету, харнессу и сроку; ключ подписи свой на каждый харнесс. Повтор или подмена предмета → отказ. **[есть]** |
| Модель «галлюцинирует» и выдаёт ложное | Детерминированный гейт: валидатор — отдельный контур, подписывает ScoreCard; ответ без подтверждения источниками не выдаётся. Модель — советник, не авторитет. **[есть]** |
| Вредоносный или ошибочный адаптер системы | Адаптер проходит статический разбор и профиль валидатора (без сети и секретов в коде, импорты из белого списка, только чтение), исполняется в песочнице; доступ к системе — через мост харнесса. **[есть]** |
| Секреты в коде/логах | Секреты только в хранилище: ссылки `env:` и `vault:` (AES-256-GCM, привязка к харнессу и системе). Наружу и в журнал идёт только ссылка. В репозитории и логах секретов нет (история git сверена). **[есть]** |
| Бесконтрольный расход/действия | Бюджет-гард: лимиты на установку, в сутки на харнесс и на ЦС; превышение — отказ до вызова модели. Запись в системы — только на уровнях автономии L1/L2, которые включает человек; инцидент возвращает на L0. **[есть]** budget/изоляция; **[MVP]** запись L1/L2 |

## Данные и их границы

- **Что покидает харнесс:** только обезличенный навык — через валидатор (профиль Skill, проверка на идентификаторы) и согласие автора. Сырые данные, ответы, память, карта систем — не покидают.
- **Что уходит во внешнюю модель:** запрос после DLP (без ПДн клиентов). Можно перейти на модель **в вашем контуре** (локальный OpenAI-совместимый endpoint) — контракты и работа не меняются.
- **Хранение:** PostgreSQL, у каждого сервиса своя роль и схема; строки размечены `harness_id`/`company_id`, проекция проверяется на стороне хранилища.

## Контроль доступа и аутентификация

- Вход в кабинет — Telegram Login (OpenID Connect + PKCE); сессии и CSRF; cookie `Secure`/`HttpOnly`/`SameSite=Strict`.
- Подключение систем: доступ вводит человек в кабинете, он шифруется в хранилище и не возвращается ни в одном ответе API.
- Внешняя поверхность знаний — только MCP, только чтение, scope на клиента из политики, каждый вызов — в журнал.

## Аудит и наблюдаемость

- **Журнал харнесса — append-only**, с provenance: работы, отчёты, решения, выпуск и применение согласий, отказы не-куратору, вызовы адаптеров, публикации навыков; у записей — источники и ссылка на проверку валидатора.
- Стоимость модели — отдельной строкой на харнесс и на ЦС.
- Мета-мозг журналирует каждый вызов (включая MCP) со scope клиента.

## Размещение

- **Внешний контур (SMB):** один `docker compose` на VPS; наружу публикуется только кабинет за HTTPS reverse proxy, остальные сервисы — во внутренней сети. Внешняя модель (DeepSeek) + DLP.
- **В контуре заказчика [план по развёртыванию, контракты готовы]:** тот же стек в вашей сети с локальной моделью — данные не покидают периметр. Переход не меняет контракты и способ работы (OPEN-06).
- Рядом с другими сервисами: отдельный проект, своя сеть и БД; Telegram-опрос не запускается, если у токена уже есть вебхук (не перехватывает чужого бота).

## Что ещё в разработке (честно)

- Действия с записью в системы (L1/L2) и профиль валидатора Action — проектно заложены, реализуются.
- OAuth-авторизация MCP вместо статических токенов клиентов.
- Внешний secret store (Vault) вместо env/vault-lite — формат ссылок не меняется.

## Что проверить при приёмке

- Нет секретов в ответах API, логах, журнале, трейсе (есть только ссылки) — тест GT-c1-13.
- Данные другого харнесса недоступны по чужому `harness_id` — GT-c1-06.
- ПДн клиента не появляются в теле запроса к внешней модели — GT-c2-07/08.
- Ответ без валидного ScoreCard и источников не выдаётся — R-04.
- Подменённый дистрибутив не ставится (проверка SHA-256 в загрузчике).
