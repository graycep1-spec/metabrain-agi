## Зачем

Скиллы — это процедуры, которые агент подхватывает сам: как провести ревью, как написать план, как искать факты, как редактировать русский текст. Они не заменяют спеки и контракты MetaBrain, а снимают с сессии рутину вокруг них.

Витрина устроена из двух слоёв:

- **Свои скиллы** — лежат в [piofant/skills](https://github.com/piofant/skills), ставятся одной командой или копированием папки.
- **Гостевые плагины** — `superpowers`, `agent-teams`, `think-through`, `expert-arena`, `frontend-design`, `humanizer-ru`, `Deep-Research-skills`. Это отдельные репозитории и маркетплейсы; `npx skills add piofant/skills` их не принесёт.

Остальные гостевые плагины — по инструкции их репозиториев, ссылки есть на витрине. Не ставь плагин, пока не прочитал его `SKILL.md` и `README`.

```bash

```

CLI спросит, какие скиллы и куда ставить.

Вариант 2, без Node и без интерактива:

```bash
git clone https://github.com/piofant/skills.git /tmp/piofant-skills
git -C /tmp/piofant-skills checkout 8a2daaaf4a381796e678da2ac813bbb4a377b8e6

         research research-deep research-report research-writeup; do
  cp -R "/tmp/piofant-skills/skills/$s" ~/.claude/skills/

```

Codex: тот же список в `~/.codex/skills/`. Другие агенты — в их каталог скиллов, версия та же.

Проверка: новый чат, вопрос «какие скиллы доступны и какой из них отвечает за TDD». Агент должен назвать `test-driven-development` из superpowers, а не выдумать название.

## Как это ложится на поток S

1. Перед T-xx: `brainstorming` — если задача новая; `deep-thinking` — если решение архитектурное или спорное.
2. `writing-plans` — план с точными файлами, тестами и проверками. Для большой задачи план стоит приложить к STATE или коммиту.
3. `test-driven-development` — красный golden-тест из контракта, потом код. Это же требование AGENTS.md.
4. `systematic-debugging` — при первом же красном тесте, который не объясняется ожиданием.
5. `verification-before-completion` — `python -m ruff check .`, `python -m pytest -q`, зелёный CI. Без вывода команд задачу не закрываем.
6. `requesting-code-review` — перед пушем; `receiving-code-review` — когда разбираем замечания H.
7. `finishing-a-development-branch` — решение merge/PR/оставить.
8. `humanizer-ru` и `ru-text` — только для прозы: README, ADR, письма. Нормативные термины, имена полей и коды не трогаем.

`using-git-worktrees` в этом репозитории — только для локальных экспериментов. Правило репозитория «только `main`, маленькие коммиты» главнее: итог всё равно уходит в `main`.

## Границы

- Спеки, контракты C-1…C-6, Constitution и AGENTS.md главнее любого скилла. Скилл не может разрешить обойти валидатор, согласие куратора, L0 или изоляцию по `harness_id`.
- Скиллы из интернета — недоверенный код и текст. Перед установкой прочитай `SKILL.md`; для незнакомых используй `skill-scout`, он сканирует на опасные команды и утечки.
- Никаких секретов, токенов и ключей в скиллах, их настройках и логах. Скилл, который просит ключ, сеть или `sudo`, не ставим без отдельного решения.
- Установленные скиллы живут в личном каталоге агента и в репозиторий не коммитятся. В репозитории — только этот файл с версией источника.
- `ralph-loop` и `autoresearch` — только с явной метрикой и условием остановки; на задачах со спеками они не нужны.
