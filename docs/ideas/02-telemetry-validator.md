# Телеметрия, валидатор и дистиллят

Статус: валидатор (C-4) с профилями и подписанным ScoreCard — **реализован**
(демо-срез, ADR-016). Полный контур телеметрии с проверками V1–V7 и дистиллятом —
**планируется** и описан здесь как целевая модель.

## 1. Назначение

Наблюдаемость харнесса как append-only контур:

```text
продюсеры → единый конверт → журнал → проверки V1–V7 → дистиллят → RO-API
```

Продюсеры: runtime работ, адаптеры, рой, валидатор, мета-мозг, кабинет.

## 2. Конверт телеметрии

Ключевые поля события:

- `event_id`, `trace_id`, `span_id`, `parent_span_id`;
- `kind` (order/process/employee/meta/…), `stage`, `entity`;
- `status_before`, `status_after`, `action`, `outcome`, `error`, `cost`;
- `producer` (name, version);
- `payload` (редактируется);
- `validation` (verdict, score, findings).

Инварианты:

- обязательные поля проверяются до записи;
- `event_id` детерминирован — для идемпотентности и дедупликации;
- секрет в payload → запись отклоняется;
- PII редактируется до сохранения (см. принцип 6);
- канонический контекст → `context_hash` (sha256).

## 3. Журнал

- Append-only; дедуп по `event_id` / `context_hash`.
- Карантин: `attempts`, `retry_after`, разбор отложенных событий воркером.
- Файловый буфер переживает рестарт; при переполнении вытесняются `ok`-события,
  ошибки и гейты сохраняются, с честной метрикой потерь.
- Backend: память (эталон семантики) или PostgreSQL (как у мета-мозга, ADR-018).

## 4. Проверки V1–V7

| Чекер | Что проверяет | Вердикт при провале |
|---|---|---|
| V1 schema | обязательные поля, словари | FAIL |
| V2 causality | переход статуса соответствует действию | FAIL |
| V3 grounding | факты опираются на источники | FAIL |
| V4 policy/PII | политики, секреты, PII | FAIL |
| V5 outcome | терминальная ошибка шага | FAIL |
| V6 replay | целостность trace/span | UNVERIFIED |
| V7 LLM-судья | смысловая оценка (advisory) | не отменяет FAIL |

Вердикты: `PASS`, `PASS_WITH_NOTES`, `FAIL`, `UNVERIFIED`.

Правила (C-4, ADR-016):

- `FAIL` важнее `UNVERIFIED`: известный дефект полезнее неизвестности.
- Инфраструктурная ошибка (`llm_unavailable`, `timeout`, `source_unavailable`) →
  `UNVERIFIED` + карантин, а не `FAIL`.
- V7 не отменяет blocking-находку; его «reject» на валидной траектории даёт
  `PASS_WITH_NOTES`, «ok» не спасает `FAIL`.
- V2 использует существующую машину статусов, не дублирует таблицу переходов.

Это обобщение профилей валидатора MetaBrain (Answer · Passport · Adapter · Action ·
Skill, C-4): каждый профиль — набор чекеров, вердикт подписывается валидатором,
критик из роя готовит мнение, но подпись ставит только валидатор (ADR-026).

## 5. Дистиллят (сигнал траектории)

- Строится только из проверенной траектории; `UNVERIFIED` не дистиллируется.
- Поля: `context_hash`, `root_cause`, `fix_candidate`, `confidence`, `provenance`,
  `cluster`.
- Детерминированные правила + advisory LLM-резюме.
- PII редактируется; сигнал без провенанса отклоняется.
- Идемпотентность по `signal_id`.

Дистиллят — вход для мета-мозга: см.
[03-meta-brain-self-improvement.md](03-meta-brain-self-improvement.md).

## 6. RO-API

Только чтение: `traces`, `validations`, `distillates`, `quarantine`.

- 405 на мутации; доступ владелец/админ;
- фильтры и пагинация;
- payload отдаётся уже отредактированным.

## 7. Точки встраивания в MetaBrain

- конверт/журнал/проверки — новый модуль телеметрии рядом с валидатором (C-4);
- оркестрация шага: `Append → Validate → Build → RecordSignal | Quarantine`;
- RO-роуты в API харнесса (C-1), вкладка в кабинете;
- события в журнал (C-3-совместимо).
