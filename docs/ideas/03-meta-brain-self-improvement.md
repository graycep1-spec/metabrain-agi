# Мета-мозг: самосовершенствование через гейт

Статус: **спроектировано** (ADR-029 операционализирует C-006), реализация — задача
T-37. Мета-мозг как хранилище навыков с полнотекстовым ретривалом и политикой-файлом
уже есть (C-5, ADR-018). Ниже — целевой контур обучения на траекториях.

## 1. Назначение

Мета-мозг превращает проверенный опыт в переиспользуемые знания и **предложения**
действий. Ключевой инвариант: **он не применяет изменения сам — только через
ревью-гейт куратора** (ADR-029). Автономной правки запущенного экземпляра нет.

## 2. Траектории

- Append-only память проверенных сигналов (из дистиллята,
  [02-telemetry-validator.md](02-telemetry-validator.md)).
- Дедуп по `signal_id` и context-ключу.
- Фильтры: kind, stage, outcome, score, время.
- Кластеры: count / success / failure / score.
- «Лучшее» — top-N только подтверждённых playbooks с провенансом; пусто → честная
  деградация (а не выдумка).
- В MVP — ранжирование по свежести и фильтрам, без embeddings (ADR-018).

## 3. Playbooks

Жизненный цикл:

```text
candidate → confirmed | rejected
```

- Подтверждает только человек.
- Подтверждённая версия **неизменяема**.
- Отклонённая сохраняется — это история решений.
- Playbook содержит: контекст, root cause, fix, ограничения, провенанс.

Это тот же путь, что у навыков MetaBrain: из одобренной рекомендации → навык, без
автоподбора по релевантности в демо-срезе (ADR-027).

## 4. Действия

```text
Propose → Approve (человек/политика) → Apply
```

- Без гейта — отказ (`gate_required`).
- Идемпотентность по `action_id`.
- Цель получает `playbook_ref`, а не сырые логи и PII.
- Исполнители (appliers): заказ, процесс (ADR-032), сотрудник (навык/политика).
- Ошибка применения → `failed`, а не «тихий успех».

## 5. Самосовершенствование политик

- Версии политики: `shadow → canary → stable`.
- Повышение версии — только с `approved_by`.
- Откат (rollback) в stable всегда возможен.
- Политика, отключающая валидатор / гейт / аудит, **отклоняется**.
- Shadow не влияет на stable.

Это и есть «агент-отладчик видит телеметрию и дорабатывает экземпляр» — но
безопасно: он готовит предложение, а применение проходит валидатор и согласие
куратора. Никакого самоперезаписывания кода на лету.

## 6. Инварианты (почему это безопасно)

- Нельзя применить действие без approve.
- Нельзя подтвердить playbook без провенанса.
- Нельзя изменить подтверждённую версию.
- Нельзя повысить политику без человека.
- Нельзя отключить проверки политикой.

## 7. RO-API

Только чтение: `trajectories`, `playbooks`, `actions`, `policies`. 405 на мутации;
доступ владелец/админ; без сырых PII.

## 8. E2E, к которому идём

```text
инцидент → телеметрия → валидатор → дистиллят → рекомендация
        → ревью куратора → действие → аудит (RO)
```
